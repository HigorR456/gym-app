# Internationalization (i18n)

The app must be built with internationalization in mind from the start.

## Initial languages

- EN
- ES
- DE

## Rules

- Don't assume text has the same length across languages.
- The UI must support longer text without breaking layout.
- Exercise names must use the localized fields provided by the dataset whenever available (see [Dataset & Licensing](dataset-and-licensing.md)).
- All interface text must use translation keys — don't hardcode UI strings inside components (see [Settings](../features/settings.md)). One narrow exception: the RepDB attribution line on the About section (see [Settings](../features/settings.md), "About") is a license-mandated exact string, hardcoded on purpose — translating it would make it no longer that exact string.
- The selected language must persist locally.

## Implementation notes

- Library: `i18next` + `react-i18next`, with `expo-localization` for the initial device-locale guess. Resource files live in `src/i18n/locales/{en,es,de}.json`, loaded eagerly (not lazy/remote) — the whole catalog is small and must work fully offline.
- Initial language is the device locale if it's one of EN/ES/DE, otherwise EN. This is only a first guess: the persisted preference (once one exists) always overrides it — see [Settings](../features/settings.md).
- Persistence uses the `app_settings` table (key `language`) via `src/data/sqlite/repositories/appSettingsRepository.ts`, not a separate storage library — see [Database Schema](database-schema.md). Reading/applying the persisted preference happens once SQLite is ready (`src/i18n/useLanguagePreference.ts`'s `useApplyPersistedLanguagePreference`), which is why it's a short-lived effect rather than part of `i18next.init()` itself.
- `useApplyPersistedLanguagePreference` (the mount-time "read the persisted value, then apply it" effect) must only ever be called once, from the app root (`_layout.tsx`) — never from a screen. Calling it a second time (found in [Settings](../features/settings.md)'s language picker) was a real bug: each call site's own read is an uncoordinated async round-trip with no way to know a newer change happened in between, so a screen's own copy of that read could resolve *after* the user picked a different language there and blindly re-apply the stale value it read before the tap, visibly reverting the change (and sometimes re-correcting a moment later, if yet another pending read resolved last). Anything that only needs the current language and a setter — like the Settings screen — uses the side-effect-free `useLanguageSetting` instead.
- Calling the hook only once wasn't sufficient by itself: its effect body could still re-run more than once over the component's lifetime (an effect's dependency array only controls *when* it re-runs, not a guarantee that it never does), and each re-run repeated the same "read persisted, then apply" round-trip — so a language change could still, in some cases, be followed by the effect re-firing and re-applying whatever it had just (re-)read. Fixed with an `initializedRef` guard in `useApplyPersistedLanguagePreference` that makes the load-and-apply logic run at most once per app lifetime, no matter how many times the effect itself is invoked.
- `useLanguageSetting`'s `setLanguage` had a second, related race, found the same way (live testing) after the first one was fixed: it's two awaited steps (`i18n.changeLanguage`, then `setAppSetting`), so tapping through several languages quickly starts multiple overlapping calls with no guaranteed resolution order — reproduced live as Deutsch → español → Deutsch settling on español, because that middle call's pair of awaits happened to resolve last. Fixed by serializing every call through a single in-flight chain (`pendingRef`/`nextRef` in `useLanguagePreference.ts`) that always ends up processing the *latest* requested language last, coalescing anything requested while a change was already in flight instead of letting concurrent calls race each other.
- Translation keys are namespaced by screen/area (e.g. `tabs.workout`); there's no flat global namespace. All three locale files must have exactly the same key set — a mismatch is a bug, not a fallback case to design around.
