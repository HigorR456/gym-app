# Internationalization (i18n)

The app must be built with internationalization in mind from the start.

## Initial languages

- EN
- ES
- DE

## Rules

- Don't assume text has the same length across languages.
- The UI must support longer text without breaking layout.
- Exercise names must use the localized fields provided by the dataset whenever available (see [Dataset & Licensing](dataset-and-licensing.md)).
- All interface text must use translation keys — don't hardcode UI strings inside components (see [Settings](../features/settings.md)).
- The selected language must persist locally.

## Implementation notes

- Library: `i18next` + `react-i18next`, with `expo-localization` for the initial device-locale guess. Resource files live in `src/i18n/locales/{en,es,de}.json`, loaded eagerly (not lazy/remote) — the whole catalog is small and must work fully offline.
- Initial language is the device locale if it's one of EN/ES/DE, otherwise EN. This is only a first guess: the persisted preference (once one exists) always overrides it — see [Settings](../features/settings.md).
- Persistence uses the `app_settings` table (key `language`) via `src/data/sqlite/repositories/appSettingsRepository.ts`, not a separate storage library — see [Database Schema](database-schema.md). Reading/applying the persisted preference happens once SQLite is ready (`src/i18n/useLanguagePreference.ts`), which is why it's a short-lived effect rather than part of `i18next.init()` itself.
- Translation keys are namespaced by screen/area (e.g. `tabs.workout`); there's no flat global namespace. All three locale files must have exactly the same key set — a mismatch is a bug, not a fallback case to design around.
